# DishLab — робота через Herdr

Як чотири ролі працюють паралельно, спілкуються між собою і не заважають одна
одній. Це операційний документ: правила git лежать у `CLAUDE.md` / `AGENTS.md`,
рішення про продукт — у `DECISIONS-MVP.md`.

---

## 1. Ролі та панелі

Чотири ролі, чотири сесії — не шість. `tester` і `merger` як окремі ролі
прибрані: для двох активних front-ів (backend/mobile) виділений тестер і
виділений мерджер простоювали більше, ніж працювали, а кожна зайва сесія — це
повний холодний контекст (`CLAUDE.md`/`AGENTS.md`/`HERDR-WORKFLOW.md` і
репозиторій наново).

| Панель | Роль | Робочий каталог | Володіє |
|---|---|---|---|
| `w4:p1` | `ceo-advisor` | основний клон | скоуп, пріоритети, рішення |
| `w4:p5` | `product-manager` | основний клон | декомпозиція, DoD, розподіл задач, механічний гейт і мердж |
| `w4:p4` | `backender` | власний worktree | `backend/`, включно з власними тестами |
| `w4:p6` | `mobile-dev` | власний worktree | корінь репо (KMP/Compose), включно з власними тестами |

`product-manager` тепер єдина роль, що мержить у `master` — вона й раніше
сиділа в основному клоні, переносити нікуди не треба. Це свідомий компроміс,
не забуте правило: `tester`/`merger` розділялись навмисно, щоб автор коду не
міг пропустити власну роботу в `master` без стороннього ока. Тепер це око —
`product-manager` з двома механічними перевірками (розділ 9), а не повне
рев'ю; сліпа зона залишається, ціна прийнята свідомо заради двох сесій замість
чотирьох.

`founder` — це власник, не агент. Його задачі (акаунт Play, похід у магазин,
домен, політика приватності) не виконує ніхто інший.

### Межі — що роль НЕ робить

Найдорожча помилка в цій схемі — не помилка в коді, а роль, яка вийшла за свою
зону. Вона тягне чужий контекст, платить за нього токенами і робить роботу,
яку хтось уже робить паралельно.

| Роль | Читає код | НЕ робить | Замість цього |
|---|---|---|---|
| `ceo-advisor` | **ні** | не пише код, не досліджує репо, не планує задачі | питає PM |
| `product-manager` | **ні** (лише запускає 2 команди гейту з розділу 9 — вивід build green/red і число, не diff) | не пише і не читає код, не виправляє провалений гейт | повертає задачу авторові |
| `backender` | так, `backend/` | не чіпає клієнт, не мержить, не пушить | заводить задачу `mobile-dev` |
| `mobile-dev` | так, корінь | не чіпає `backend/`, не мержить, не пушить | заводить задачу `backender` |

**Правило одне: потрібен факт із чужої зони — питаєш роль, яка нею володіє.
Не йдеш дивитись сам.** Промт коштує сотні токенів, самостійне дослідження
репозиторію — десятки тисяч.

Це стосується і `ceo-advisor`: оцінка скоупу робиться з опису проблеми, а не з
читання реалізації.

## 2. Життєвий цикл задачі

```
PM: herdr task create ... --dod "…" --branch feat/t-13-… --role mobile-dev
        ↓
dev: herdr task next --claim → herdr task claim t-13 --worktree →
     код + тести з DoD → коміти
        ↓
dev: herdr task complete t-13 --notify w4:p5 "готова, гілка feat/t-13-…"
        ↓
PM: гейти (розділ 9) → git merge --no-ff → git push origin master →
    herdr task merge t-13 --notify w4:p6 "змерджено"
    (розблоковує --blocked-by t-13, сам прибирає worktree)
```

Один ланцюг для всіх типів задач — без розгалуження `feat/fix` проти
`docs/chore`, як було раніше. Те розгалуження існувало, щоб не ганяти дрібну
задачу через `tester`, якого більше немає. Тести для `feat`/`fix` пише сам
автор з DoD задачі — це і є заміна `tester`-а, з відомим компромісом (розділ 1:
автор коду й автор тесту — одна особа, спільна сліпа зона).

## 3. Як почати роботу (кожен агент, один раз за сесію)

```bash
export JAVA_HOME=/home/denis/work/IDE/android-studio/jbr
herdr agent role get                     # переконатись у своїй ролі
herdr task next --claim                  # взяти наступну готову задачу
```

**До коду — власний worktree через herdr, не вручну.** Checkout у git
глобальний для клона: без окремого каталогу агенти перезапишуть файли одне
одному без жодного попередження.

```bash
herdr task claim t-<id> --worktree
cd ~/.herdr/worktrees/DishLab/task-t-<id>
cp /home/denis/work/Projects/DishLab/androidApp/google-services.json \
   ~/.herdr/worktrees/DishLab/task-t-<id>/androidApp/
```

Claim ідемпотентний для того самого агента — повторний виклик просто
повторює спробу checkout, не звільняючи задачу. Шлях детермінований з ID
задачі (`~/.herdr/worktrees/DishLab/task-t<id>`), тож PM пізніше на гейті
(розділ 9) обчислює його сам, без додаткового поля в промті — та сама
причина, що й раніше з `/tmp/dishlab-t<id>` (пакетний мердж, розділ 12: dev
бере наступну задачу до того, як попередню змерджено, і колізії шляхів не
має бути). Гілка на checkout береться з поля `branch` задачі — його задає
`product-manager` при створенні (`--branch <type>/t-<id>-<slug>`); якщо не
задати, herdr підставляє власну `task/t-<id>`, що ламає конвенцію іменування
гілок нижче.

`androidApp/google-services.json` untracked (і вже виключений кореневим
`.gitignore`), але `androidApp` застосовує `googleServices`: без локальної
копії Android-збірка падає, і це не помилка коду. herdr про цей файл не знає
— копіювання лишається ручним кроком. Файл не комітити та не змінювати для
нього `.gitignore`.

Виняток — `product-manager` і `ceo-advisor`: коду не пишуть, worktree не
потрібен.

## 4. Як писати промт агенту

```bash
herdr agent prompt <панель> "<текст>"
herdr agent prompt w4:p6 "Візьми t-13" --wait --until idle   # дочекатись завершення
```

**Промт має містити рівно чотири речі:**

1. **ID задачі** — `t-13`, щоб агент підтягнув `body` з дошки, а не гадав
2. **Що зробити** — одним реченням
3. **Кому передати** — панель наступної ролі
4. **Межу** — чого робити не можна

Приклад робочого промту:

```
Візьми t-13 через `herdr task next --claim`. DoD — у полі dod задачі.
Підніми worktree: herdr task claim t-13 --worktree, працюй у ньому.
Коміти за конвенцією з CLAUDE.md, гілку в origin НЕ пушити, PR НЕ відкривати.
Коли готово: herdr task complete t-13 --notify w4:p5 "готова, гілка feat/t-13-<slug>".
```

**Чого в промті бути не повинно:** переказу DoD (він у задачі), пояснення
архітектури (вона в `CLAUDE.md`), списку файлів (агент знайде сам).

**`--notify` на `task complete`/`task merge` замінює окремий `agent prompt`.**
Ціль валідується до мутації дошки — невалідна панель валить увесь виклик, і
задача лишається як була (не "виконана, але без сповіщення"). Це і є
механізм, що замінив попереднє правило "робота без промту вважається
невиконаною": раніше воно було текстом у charter, тепер — властивістю
самого виклику.

**`herdr task note t-13 "<текст>"`** — робочий нотаток на задачі: що зараз
відбувається, що вирішено, що не вийшло, наступний крок. Писати на
природних чекпоінтах, не тільки перед передачею — агент, що вичерпав
токени, вже не встигне його написати. Саме це читає `agent handover`
(нижче), коли роль передають іншій сесії.

У панелі задач (TUI) `m` — швидкий мердж, `d` — швидкий перегляд DoD ("done
when"); у сайдбарі `✉N` показує чергу непрочитаних промтів на панель, тож
повідомлення більше не злипаються одне з одним.

## 5. Хто кому пише

**Правило: потреба в чужій зоні ніколи не означає очікування.** Заводиш задачу
тій ролі, блокуєш свою, береш наступну готову.

```bash
herdr task create "POST /api/v1/recipes/batch" --role backender --body "Потрібно для t-19"
herdr task update t-19 --blocked-by t-40
herdr task next --claim          # береш іншу задачу, не чекаєш
```

Заблокована задача повертається в чергу автоматично, коли PM реально змержить
блокуючу (`herdr task merge`) — не коли автор лише зробить `task complete`.
До мержу коду блокуючої задачі фізично ще немає в `master`, і herdr тепер це
розрізняє сам (`TaskStatus::Merged`, окремий від `Done`).

**Маршрутизація за типом питання:**

| Питання | Кому | Чому |
|---|---|---|
| Потрібен ендпоінт / поле в DTO / міграція | `backender`, задачею | технічна залежність, не рішення |
| Незрозумілий DoD, суперечність у задачі | `product-manager` | він її писав |
| Задача виходить за MVP, потрібна нова фіча | `product-manager` | він вирішує, чи це питання скоупу |
| Гілка готова до мержу | `product-manager` | гейти й мердж — тепер його зона |
| PM-гейт не пройшов (build red / тестів стало менше) | назад авторові задачі | PM код не виправляє |

### До `ceo-advisor` звертається тільки `product-manager`

`backender` і `mobile-dev` **не пишуть `ceo-advisor` ніколи** —
навіть коли впевнені, що знайшли питання скоупу. Кажуть PM, він вирішує.

Причина не в ієрархії, а в контексті. `ceo-advisor` не читає код: рішення про
скоуп ухвалюється з опису проблеми. Технічний звіт, надісланий йому напряму
(«ендпоінт віддає 404»), затягує його в чужу зону, і за два кроки він
розбирається в реалізації замість того, щоб оцінювати продукт.

PM — фільтр. Більшість того, що виглядає як питання скоупу, ним не є: це
незрозумілий DoD, помилка в задачі або технічна залежність. До
`ceo-advisor` доходить лише те, що справді змінює межі MVP — з уже перевіреним
фактом і сформульованим питанням.

Симетрично: `ceo-advisor` не пише виконавцям напряму. Рішення йде в PM, PM
перетворює його на задачі й промти.

### Кінець ланцюга — завжди `product-manager`

Задача, яку зроблено, але про яку не сказано PM'у, для проєкту не існує. Дошка
показує статус; вона не показує, що саме побачить власник на пристрої.

| Подія | Хто пише | Кому | Що саме |
|---|---|---|---|
| Заблокувався, зупинився, не знає що далі | dev | `w4:p5` | на чому став |
| Задача виявилась ширшою, ніж її `body` | будь-хто | `w4:p5` | що вилізло |

(Мердж більше не потребує окремого повідомлення "до `w4:p5`" — `product-manager`
сам його виконує і вже знає результат.)

**До власника не пише ніхто, крім `product-manager`.** Власник не читає код і не
читає дошку — він ставить APK на телефон. Технічний звіт напряму йому змушує
його розбиратись у реалізації замість оцінки продукту.

**PM пише власнику лише тоді, коли є що ставити на телефон** — змерджений
інкремент, який змінює поведінку застосунку. Не після кожної закритої задачі:
«t-16 готова» власнику не говорить нічого, «критичний баг навігації у master,
можна перевіряти» — говорить усе.

Після цього PM мовчить. Наступний крок — за власником.

**Зміна скоупу — тільки через `ceo-advisor`.** Агент, який дописує фічу «бо
логічно», ламає правило скоупу з `PRD-MVP.md`, і про це ніхто не дізнається,
поки не з'ясується, що реліз відповідає не на те питання.

## 6. Хто створює задачі

| | Може створювати |
|---|---|
| `product-manager` | будь-які задачі будь-якій ролі — основне джерело |
| `ceo-advisor` | задачі PM'у і `founder` |
| `backender` / `mobile-dev` | **тільки задачі-блокери** — те, без чого їхня стоїть |

Агент не заводить задачі «на майбутнє» і «щоб не забути». Дошка — черга роботи,
а не список ідей. Ідея йде до `ceo-advisor`, і якщо вона в скоупі, PM заведе
задачу.

## 7. Обов'язкові поля задачі

```bash
herdr task create "<що зробити>" \
  --role <роль> \
  --dod "<перевірна умова>" \
  --body "Контекст: <навіщо>. Файли: <підказка>" \
  --priority <low|normal|high> \
  --blocked-by t-N
# відповідь містить id (наприклад t-63) — гілку до нього не знати
herdr task update t-63 --branch feat/t-63-<slug>
```

**Задача без `--dod` — зламана, і тепер herdr сам це не пускає:**
`task create --role <X>` без `--dod` завершується помилкою (задачі без
`--role`, наприклад для `ceo-advisor`, можна створювати без DoD). Автор пише з
DoD і код, і тест: нечітка умова — тест під готову реалізацію, а не намір.
Зовнішній гейт цього все одно не зловить (PM перевіряє лише build і кількість
тестів, розділ 9, не відповідність задуму) — обов'язковість поля прибирає
лише найгрубіший випадок (DoD відсутній узагалі), не підміняє сам гейт.

**`--branch` теж обов'язковий для задач з `--role`, але другим викликом.**
`create` не приймає `--branch` з ID усередині — ID видає сама команда, тож
раніше створення його ще нема. herdr це не перевіряє (на відміну від
`--dod`), тому пропустити легко: без `--branch` `herdr task claim --worktree`
(розділ 3) підставляє власну гілку `task/t-<id>` — коміти підуть, але гілка
випаде з конвенції `<type>/t-<id>-<slug>`.

## 8. Паралельність

Одночасно активні: `backender`, `mobile-dev` — два worktree, дві гілки.
`product-manager` і `ceo-advisor` сидять в основному клоні й коду не пишуть,
тож окремого worktree не займають.

**Не паралеляться:**
- дві задачі одного модуля різними агентами — зіткнуться у тих самих файлах
- `product-manager` — мержить строго по одній гілці, послідовно

Реальна межа паралельності — два фронти (клієнт і бекенд). Третій dev-агент в
одному з цих модулів не прискорить нічого: він або чекатиме, або полізе в
чужий файл.

**Пакетна робота одного виконавця (рішення власника 2026-08-07).** Коли в
черзі ready-задач кілька — виконавець (`backender`/`mobile-dev`) бере й
робить кілька за один захід, кожну в своїй гілці, і звітує PM про всі одразу
(кілька гілок в одному повідомленні), а не одну задачу → звіт → чекати
наступний промт → наступна задача. Орієнтир — до ~2–3 тис. рядків сумарно за
захід, коли задач багато; коли задача одна (черга коротка) — звітувати можна
й раніше, розтягувати штучно не треба. Мета — менше циклів
"звіт-очікування-промт" на PM, а не менше коду за задачу.

**Пакетне заведення задач, бік PM (рішення власника 2026-08-07).** Той самий
принцип на боці декомпозиції: коли PM заводить кілька пов'язаних дрібних
пунктів (типово — серія фідбеків власника після тестування на пристрої), вони
йдуть в ОДНУ задачу з нумерованим DoD (див. `t-72`), а не кожен окремою
задачею. Окрема задача виправдана лише коли: різні ролі/worktree, реальне
блокування, що вимагає окремого мержу першим, або обсяг, що зробить один
контекст непідйомним. Інакше — один `task create`, одна гілка, один мердж:
менше циклів гейт-мердж на PM без падіння якості перевірки кожної гілки.

Коли задач у черзі мало (одна-дві) — це правило не примушує штучно чекати
третьої, щоб набрати обсяг. Правило про механічний гейт (розділ 9) не
змінюється: PM все одно валідує кожну гілку окремо перед мерджем, навіть якщо
прийшли пачкою.

## 9. Гейти `product-manager` — два, обидва механічні

PM гейтить прямо у worktree дева (`~/.herdr/worktrees/DishLab/task-t<id>` —
шлях детермінований з ID, розділ 3), не створюючи власний: там уже стоїть
скопійований `google-services.json`, і дублювати цю підготовку заради
перевірки немає сенсу.

1. Кількість тестових файлів не зменшилась:
   `find . -name '*Test.kt' | wc -l` до і після
2. Збірка зелена (`./gradlew build` у корені для mobile-задач,
   `cd backend && ./gradlew build` для backend-задач)

PM не читає diff і не оцінює якість тестів — тільки ці дві механічні цифри.
Падіння кількості тестів без явного дозволу власника — відмова в мержі. Це
захист від патології «не можу полагодити тест — видалю тест», що раніше
покривав окремий `tester`.

**Чого цей гейт свідомо не ловить:** тест, який технічно проходить, але не
перевіряє намір DoD (сліпа зона автора коду й автора тесту в одній особі —
розділ 1). Ціна прийнята заради двох сесій замість чотирьох.

### Перевірка на фізичному пристрої

Окремої ролі з постійним доступом до пристрою більше немає — це тепер гейт
`founder`-а (розділ 10), а не частина кожного мержу. Пункт DoD, що вимагає
пристрою, чекає найближчої точки виходу (щотижня або перед тегом), а не
блокує кожен окремий мердж. Команди для такого прогону й питання, на які вони
відповідають, зберігаються та поповнюються у
[`DEVICE-TESTING.md`](DEVICE-TESTING.md).

Мерж завжди:

```bash
git merge --no-ff <гілка> -m "Merge t-<id>: <опис>"
git push origin master
herdr task merge <id> --notify <панель-автора> "змерджено"
```

`herdr task merge <id>` сам прибирає worktree, створений через `task claim
--worktree` (розділ 3) — окремого `git worktree remove` більше не треба.
Локальну гілку (`git branch -d <гілка>`) це не чіпає, її PM прибирає сам,
якщо хоче.

`herdr task merge <id>` — твердження PM, не перевірка git: herdr не лізе в
репозиторій, щоб переконатись, що код реально в `master`. Довірча модель та
сама, що й у `task complete`, просто перенесена на роль, якій менше сенсу
брехати.

### Коли валідується кілька гілок одразу (пакетний мердж, розділ 12)

PM спершу валідує кожну гілку окремо (у її власному worktree дева) — тест-
кількість і build для кожної незалежно. Мержить у `master` лише ті, що
пройшли індивідуально, і лише тоді ганяє один спільний build як підтвердження
перед `herdr task merge` для кожної. Якщо й спільний build падає, попри те що
кожна гілка пройшла окремо — це конфлікт між гілками (рідкість), і тоді
потрібне ручне бісектування (відкат мержів по одному, поки не знайдеться
винна пара). PM ніколи не штовхає в `master` те, що не пройшло хоч
індивідуальну перевірку.

## 10. Що робить власник

Не рев'ює код. Два гейти:

- **Вхід** — що будуємо, що не будуємо (через `ceo-advisor`)
- **Вихід** — раз на тиждень і перед кожним тегом: поставити APK на телефон і
  відсканувати реальний продукт у магазині, 5 хвилин

Причина другого: агенти пишуть код, агенти пишуть тести, агенти мержать. Цикл
замкнений сам на себе. Зелений `master` означає «агенти узгоджені між собою», а
не «продукт працює».

**Контроль процесу — два числа з дошки, не diff'и:**

1. `cycle time` — від `todo` до змердженого. Росте після додавання ролі — роль
   шкодить
2. частка `blocked` — блокованих більше, ніж активних, означає не нестачу
   агентів, а хибний порядок задач

**Ознака зламаного процесу:** задачі закриваються, cycle time низький, а
`recipe_opened` у продукті не росте. Машина працює ідеально й виробляє не те.

## 11. Корисні команди

```bash
herdr task list --role mobile-dev --ready      # що готове для ролі
herdr task list --open                         # усе незакрите
herdr task get t-13                            # повний body/dod задачі
herdr task claim t-13 --worktree               # взяти + підняти checkout
herdr task complete t-13 --notify w4:p5 "..."  # атомарно: готово + промт
herdr task merge t-13 --notify w4:p6 "..."     # PM, після push; прибирає worktree
herdr task note t-13 "<що зараз, наступний крок>"  # чекпоінт для handover
herdr task roles                               # зведення по ролях
herdr agent list                               # панелі та їхні ролі
herdr agent read <панель>                      # що агент вивів у термінал
herdr agent prompt <панель> "<текст>"          # надіслати промт
herdr agent handover <з-панелі> <на-панель>    # передати роль+транскрипт
herdr worktree list                            # активні worktree
```

## 12. Економія: що не проходить повний ланцюг

Найдорожче в конвеєрі — не робота, а **холодні старти на хендофах**. Кожна
передача між ролями означає, що наступний агент читає `CLAUDE.md`, `AGENTS.md`,
`HERDR-WORKFLOW.md` і репозиторій з нуля. Раніше три ролі на задачу
(dev → tester → merger) означали три повні контексти ще до першого рядка
роботи; тепер ланцюг для будь-якого типу задачі — dev → PM, один хендоф.

**Холодний старт усередині однієї ролі — інша ситуація, і для неї є
`herdr agent handover <з-панелі> <на-панель>`.** Коли сесія вичерпує токени
посеред задачі, це не хендоф між ролями (роль та сама), а заміна виконавця:
`handover` передає роль, взяту в роботу задачу й транскрипт (400 рядків) —
працює, навіть коли сесія, що передає, уже не відповідає. Новий агент усе
одно читає `CLAUDE.md`/`AGENTS.md`/`HERDR-WORKFLOW.md` (це не частина
транскрипту), але не з нуля розбирається, що саме робилось — для цього і
`herdr task note` (розділ 4): писати на чекпоінтах, а не тільки в момент
передачі, бо агент без токенів уже не встигне.

### Пакетний мерж

`product-manager` не мержить кожну гілку окремо. Накопичує 3–4 готові й
мержить разом:
`./gradlew build` — найдорожча операція конвеєра, і вона однакова для однієї
гілки й для чотирьох.

Виняток — `--priority high`: мержиться одразу.

### Простійні сесії

Роль із `ready=0` і непорожнім `blocked` не тримають відкритою. Сесія без роботи
все одно утримує контекст. Піднімати, коли PM розблокує:

```bash
herdr task list --role backender --ready
```

### Чого НЕ економимо

**Три файли контексту дублюються навмисно** — Claude читає `CLAUDE.md`, Codex
читає `AGENTS.md`. Прибрати дублювання означає, що половина агентів працюватиме
без правил.

**PM не пише код і не читає diff, навіть мержачи.** Спокуса розширити гейт до
повного рев'ю є — PM єдина роль, що бачить кожен мердж. Але це перетворить її
на вузьке горло і зруйнує причину, чому вона взагалі не читає код (розділ 1:
рішення про мердж — з двох чисел, не з diff). Якщо механічний гейт проходить,
а результат все одно зламаний — це сигнал підняти окрему `tester`-сесію для
конкретного модуля, а не змусити PM читати код "цього разу".
