# DishLab — робота через Herdr

Як шість ролей працюють паралельно, спілкуються між собою і не заважають одна
одній. Це операційний документ: правила git лежать у `CLAUDE.md` / `AGENTS.md`,
рішення про продукт — у `DECISIONS-MVP.md`.

---

## 1. Ролі та панелі

| Панель | Роль | Робочий каталог | Володіє |
|---|---|---|---|
| `w4:p1` | `ceo-advisor` | основний клон | скоуп, пріоритети, рішення |
| `w4:p5` | `product-manager` | основний клон | декомпозиція, DoD, розподіл задач |
| `w4:p4` | `backender` | власний worktree | `backend/` |
| `w4:p6` | `mobile-dev` | власний worktree | корінь репо (KMP/Compose) |
| `w4:p8` | `tester` | власний worktree | тести, вердикт |
| `w4:p2` | `merger` | **основний клон** | єдине право мержити в `master` |

`merger` навмисно сидить в основному клоні — він єдиний, кому потрібен `master`,
і єдиний, хто має право його чіпати.

`founder` — це власник, не агент. Його задачі (акаунт Play, похід у магазин,
домен, політика приватності) не виконує ніхто інший.

### Межі — що роль НЕ робить

Найдорожча помилка в цій схемі — не помилка в коді, а роль, яка вийшла за свою
зону. Вона тягне чужий контекст, платить за нього токенами і робить роботу,
яку хтось уже робить паралельно.

| Роль | Читає код | НЕ робить | Замість цього |
|---|---|---|---|
| `ceo-advisor` | **ні** | не пише код, не досліджує репо, не планує задачі | питає PM або tester |
| `product-manager` | **ні** | не пише і не читає код, не запускає збірки | питає tester про стан, dev про реалізацію |
| `backender` | так, `backend/` | не чіпає клієнт, не мержить, не пушить | заводить задачу `mobile-dev` |
| `mobile-dev` | так, корінь | не чіпає `backend/`, не мержить, не пушить | заводить задачу `backender` |
| `tester` | так, усе | не править чужий код, не мержить | повертає задачу авторові |
| `merger` | diff | не править код заради зелених тестів | повертає задачу авторові |

**Правило одне: потрібен факт із чужої зони — питаєш роль, яка нею володіє.
Не йдеш дивитись сам.** Промт коштує сотні токенів, самостійне дослідження
репозиторію — десятки тисяч.

Це стосується і `ceo-advisor`: оцінка скоупу робиться з опису проблеми, а не з
читання реалізації.

## 2. Життєвий цикл задачі

```
PM створює задачу з DoD у body
        ↓
dev: herdr task next --claim → worktree → код → коміти
        ↓
dev: herdr task complete <id> + промт наступній ролі
        ↓
   ┌────┴────────────────────────────┐
   │ feat / fix                      │ docs / chore / test
   ↓                                 ↓
tester: тести з DoD → вердикт        (одразу до merger)
   ↓                                 │
   └────────────┬────────────────────┘
                ↓
merger: гейти → git merge --no-ff → git push origin master
                ↓
merger: прибирає worktree і локальну гілку
```

**Розгалуження за типом задачі — не послаблення, а економія.** Тест на
`.gitignore` чи на текст README не перевіряє нічого, а холодний старт третього
агента коштує повного контексту. Деталі — розділ 12.

## 3. Як почати роботу (кожен агент, один раз за сесію)

```bash
export JAVA_HOME=/home/denis/work/IDE/android-studio/jbr
herdr agent role get                     # переконатись у своїй ролі
herdr task next --claim                  # взяти наступну готову задачу
```

**До першого `claim` — власний worktree.** Checkout у git глобальний для клона:
без окремого каталогу агенти перезапишуть файли одне одному без жодного
попередження.

```bash
git worktree add /tmp/dishlab-<роль> -b <type>/t-<id>-<slug>
cd /tmp/dishlab-<роль>
```

Виняток — `merger`, `product-manager` і `ceo-advisor`: коду не пишуть, worktree
не потрібен.

## 4. Як писати промт агенту

```bash
herdr agent prompt <панель> "<текст>"
herdr agent prompt w4:p6 "Візьми t-13" --wait --until idle   # дочекатись завершення
```

**Промт має містити рівно чотири речі:**

1. **ID задачі** — `t-13`, щоб агент підтягнув `body` з дошки, а не гадав
2. **Що зробити** — одним реченням
3. **Кому передати** — панель наступної ролі
4. **Межу** — чого робити не можна

Приклад робочого промту:

```
Візьми t-13 через `herdr task next --claim`. DoD у полі body задачі.
Працюй у власному worktree: git worktree add /tmp/dishlab-mobile -b feat/t-13-<slug>.
Коміти за конвенцією з CLAUDE.md, гілку в origin НЕ пушити, PR НЕ відкривати.
Коли готово: herdr task complete t-13, потім
herdr agent prompt w4:p8 "t-13 готова у гілці feat/t-13-<slug>, перевір".
```

**Чого в промті бути не повинно:** переказу DoD (він у задачі), пояснення
архітектури (вона в `CLAUDE.md`), списку файлів (агент знайде сам).

## 5. Хто кому пише

**Правило: потреба в чужій зоні ніколи не означає очікування.** Заводиш задачу
тій ролі, блокуєш свою, береш наступну готову.

```bash
herdr task create "POST /api/v1/recipes/batch" --role backender --body "Потрібно для t-19"
herdr task update t-19 --blocked-by t-40
herdr task next --claim          # береш іншу задачу, не чекаєш
```

Заблокована задача повертається в чергу автоматично, коли інша роль закриє свою.

**Маршрутизація за типом питання:**

| Питання | Кому | Чому |
|---|---|---|
| Потрібен ендпоінт / поле в DTO / міграція | `backender`, задачею | технічна залежність, не рішення |
| Незрозумілий DoD, суперечність у задачі | `product-manager` | він її писав |
| Задача виходить за MVP, потрібна нова фіча | `product-manager` | він вирішує, чи це питання скоупу |
| Гілка готова до перевірки | `tester` | |
| Тести пройшли | `merger` | |
| Тести не пройшли | назад авторові задачі | tester код не править |

### До `ceo-advisor` звертається тільки `product-manager`

`backender`, `mobile-dev`, `tester`, `merger` **не пишуть `ceo-advisor` ніколи** —
навіть коли впевнені, що знайшли питання скоупу. Кажуть PM, він вирішує.

Причина не в ієрархії, а в контексті. `ceo-advisor` не читає код: рішення про
скоуп ухвалюється з опису проблеми. Технічний звіт, надісланий йому напряму
(«ендпоінт віддає 404»), затягує його в чужу зону, і за два кроки він
розбирається в реалізації замість того, щоб оцінювати продукт.

PM — фільтр. Більшість того, що виглядає як питання скоупу, ним не є: це
незрозумілий DoD, помилка в задачі або технічна залежність. До
`ceo-advisor` доходить лише те, що справді змінює межі MVP — з уже перевіреним
фактом і сформульованим питанням.

Симетрично: `ceo-advisor` не пише виконавцям напряму. Рішення йде в PM, PM
перетворює його на задачі й промти.

### Кінець ланцюга — завжди `product-manager`

Задача, яку зроблено, але про яку не сказано PM'у, для проєкту не існує. Дошка
показує статус; вона не показує, що саме побачить власник на пристрої.

| Подія | Хто пише | Кому | Що саме |
|---|---|---|---|
| Гілку змерджено в `master` | `merger` | `w4:p5` | ID задачі, хеш мержу, тести до/після, стан збірки |
| Вердикт негативний | `tester` | авторові задачі **і** `w4:p5` | що саме не пройшло |
| Заблокувався, зупинився, не знає що далі | dev | `w4:p5` | на чому став |
| Задача виявилась ширшою, ніж її `body` | будь-хто | `w4:p5` | що вилізло |

**До власника не пише ніхто, крім `product-manager`.** Власник не читає код і не
читає дошку — він ставить APK на телефон. Технічний звіт напряму йому змушує
його розбиратись у реалізації замість оцінки продукту.

**PM пише власнику лише тоді, коли є що ставити на телефон** — змерджений
інкремент, який змінює поведінку застосунку. Не після кожної закритої задачі:
«t-16 готова» власнику не говорить нічого, «критичний баг навігації у master,
можна перевіряти» — говорить усе.

Після цього PM мовчить. Наступний крок — за власником.

**Зміна скоупу — тільки через `ceo-advisor`.** Агент, який дописує фічу «бо
логічно», ламає правило скоупу з `PRD-MVP.md`, і про це ніхто не дізнається,
поки не з'ясується, що реліз відповідає не на те питання.

## 6. Хто створює задачі

| | Може створювати |
|---|---|
| `product-manager` | будь-які задачі будь-якій ролі — основне джерело |
| `ceo-advisor` | задачі PM'у і `founder` |
| dev / tester / merger | **тільки задачі-блокери** — те, без чого їхня стоїть |

Агент не заводить задачі «на майбутнє» і «щоб не забути». Дошка — черга роботи,
а не список ідей. Ідея йде до `ceo-advisor`, і якщо вона в скоупі, PM заведе
задачу.

## 7. Обов'язкові поля задачі

```bash
herdr task create "<що зробити>" \
  --role <роль> \
  --body "DoD: <перевірна умова>. Контекст: <навіщо>. Файли: <підказка>" \
  --priority <low|normal|high> \
  --blocked-by t-N
```

**`body` без DoD — зламана задача.** `tester` пише тести саме з `body`: якщо
там немає перевірної умови, він змушений читати код розробника — і тоді тест
підтверджує реалізацію замість наміру. Це головна поломка всієї схеми.

## 8. Паралельність

Одночасно активні: `backender`, `mobile-dev`, `tester` — три різні worktree,
три різні гілки.

**Не паралеляться:**
- дві задачі одного модуля різними агентами — зіткнуться у тих самих файлах
- `merger` — мержить строго по одній гілці, послідовно

Реальна межа паралельності — два фронти (клієнт і бекенд) плюс перевірка. Четвертий
dev-агент не прискорить нічого: він або чекатиме, або полізе в чужий модуль.

---

## 9. Гейти `merger` — три, усі механічні

1. Вердикт `tester` позитивний
2. Кількість тестових файлів не зменшилась:
   `find . -name '*Test.kt' | wc -l` до і після
3. Збірка зелена

Падіння кількості тестів без явного дозволу власника — відмова в мержі. Це
захист від патології «не можу полагодити тест — видалю тест».

### Перевірка на фізичному пристрої

`tester` має доступ до фізичного Android-пристрою. Пункт DoD, який вимагає
пристрою, перевіряється саме на ньому і саме `tester`-ом. Для таких пунктів
вердикт PASS без фактичного прогону на пристрої не видається; у звіті tester
вказує лише реально виконані дії та їхній результат. Копійовані команди для
такого прогону й питання, на які вони відповідають, зберігаються та
поповнюються у [`DEVICE-TESTING.md`](DEVICE-TESTING.md).

Мерж завжди:

```bash
git merge --no-ff <гілка> -m "Merge t-<id>: <опис>"
git push origin master
git worktree remove <шлях> && git branch -d <гілка>
```

## 10. Що робить власник

Не рев'ює код. Два гейти:

- **Вхід** — що будуємо, що не будуємо (через `ceo-advisor`)
- **Вихід** — раз на тиждень і перед кожним тегом: поставити APK на телефон і
  відсканувати реальний продукт у магазині, 5 хвилин

Причина другого: агенти пишуть код, агенти пишуть тести, агенти мержать. Цикл
замкнений сам на себе. Зелений `master` означає «агенти узгоджені між собою», а
не «продукт працює».

**Контроль процесу — два числа з дошки, не diff'и:**

1. `cycle time` — від `todo` до змердженого. Росте після додавання ролі — роль
   шкодить
2. частка `blocked` — блокованих більше, ніж активних, означає не нестачу
   агентів, а хибний порядок задач

**Ознака зламаного процесу:** задачі закриваються, cycle time низький, а
`recipe_opened` у продукті не росте. Машина працює ідеально й виробляє не те.

herdr task list --role mobile-dev --ready      # що готове для ролі
herdr task list --open                         # усе незакрите

## 12. Економія: що не проходить повний ланцюг

Найдорожче в конвеєрі — не робота, а **холодні старти на хендофах**. Кожна
передача між ролями означає, що наступний агент читає `CLAUDE.md`, `AGENTS.md`,
`HERDR-WORKFLOW.md` і репозиторій з нуля. Три ролі на задачу — три повні
контексти ще до першого рядка роботи.

### Поріг за типом задачі

| Тип | Ланцюг | Чому |
|---|---|---|
| `feat`, `fix` | dev → **tester** → merger | є логіка, яку можна зламати непомітно |
| `docs`, `chore`, `test` | dev → merger | тест на `.gitignore` не перевіряє нічого |

Тип береться з префікса гілки. Сумнів — трактувати як `feat` і вести через
tester.

### Пакетний мерж

`merger` не мержить кожну гілку окремо. Накопичує 3–4 готові й мержить разом:
`./gradlew build` — найдорожча операція конвеєра, і вона однакова для однієї
гілки й для чотирьох.

Виняток — `--priority high`: мержиться одразу.

### Простійні сесії

Роль із `ready=0` і непорожнім `blocked` не тримають відкритою. Сесія без роботи
все одно утримує контекст. Піднімати, коли PM розблокує:

```bash
herdr task list --role backender --ready
```

### Чого НЕ економимо

**Три файли контексту дублюються навмисно** — Claude читає `CLAUDE.md`, Codex
читає `AGENTS.md`. Прибрати дублювання означає, що половина агентів працюватиме
без правил.

**Ролі `tester` і `merger` не об'єднуємо.** Спокуса є — обидві реактивні й часто
простоюють. Але саме їхнє розділення ловить патологію «не можу полагодити тест —
видалю тест». Автор тесту не може бути тим, хто пропускає власну роботу в
`master`.
